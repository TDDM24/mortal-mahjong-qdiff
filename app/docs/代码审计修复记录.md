## 二、关键证据

### P0-1 丢手（这是最值钱的一条）

`0b0d6c2336b144eb` 的 `review.total_reviewed = 184`，`entries` 也正好 184，但旧实现只算出 183 手。
被丢的是第 5 局（kn=4）第 19 条（i=18）、15 巡：

```
actual   = {type: dahai, pai: 4p, tsumogiri: false}   ← 手切
expected = {type: dahai, pai: 4p, tsumogiri: true}    ← 摸切（details 里只有这一条）
details  = [dahai|4p|1, dahai|9m|0, dahai|1m|0, ...]
```

手牌里本来就有一张 `4p`，又摸进一张 `4p`，玩家选择手切原来那张。Mortal 的动作空间不区分摸切/手切，
所以 `details` 里只给了一条 `dahai|4p|1`，而 `actual` 的键是 `dahai|4p|0` → 查不到 → 整手跳过。

127 份报告共 19327 条 entry，这样被丢的有 **61 条（0.316%）**。
报告本身已经给了对齐好的 `actual_index`（127 份里 100% 有），`details[actual_index]` 与 `actual` 一致率 19315/19327，
不一致的 12 条只是 `consumed` 顺序、赤五写法（`5pr` vs `5p`）这类差异。

改法：优先用 `actual_index` 取 Q；取不到时用「忽略摸切/赤五/副露顺序」的宽松键兜底。

### P0-2 暗杠崩溃

`mjai` 的暗杠事件是 `{"type":"ankan","actor":2,"consumed":["N","N","N","N"]}` ——**没有 `pai`**。
旧代码把 `ev.pai`（undefined）存进副露，之后任何走到 `visible()` 的地方都会 `tileIndex(undefined)` → 崩。
60 个暗杠事件全都没有 `pai`；随机取 40 个含暗杠的快照调 `visible()`，40 个全抛
`TypeError: Cannot read properties of undefined (reading 'replace')`。

之前跑 62 场没炸，是因为那些局暗杠之后刚好没有防守决策——属于**潜伏崩溃**，不是没问题。

### P0-3 只成立一半

- 快照时机：`dahai` 分支先删手牌、推牌河、junme+1，最后才 `st.snapshot()`，所以 `post_call` 快照是切牌后的 10 张，
  而 Mortal 的 `state.tehai` 是切牌前的 11 张 → 精确匹配必然失败。**成立，已改**（先拍快照再改状态）。
- 「立直切牌 100% 失配」：实测 98 条立直切牌 entry，96 条（98%）没精确匹配——**现象成立**，
  但成因不是「缺决策点」（`tsumo` 点是有的），而是 Mortal 对立直那一巡的 `state.tehai` 含有刚摸的牌、
  我们这边的手牌排序/对齐另有偏差。这条没做结构性重写，留到下个版本，避免一次性改动过大。

### P0-4 不成立

报告说「遇零决策局后下标错位」。实测 127 份报告，`mjai_log` 里 `start_kyoku` 的次数与 `review.kyokus.length`
**127/127 完全相等**，说明 Mortal 的 `kyokus` 不会漏掉零决策局，`kn` 下标是对得上的。
只有在「拿半截牌谱喂进来」时才可能错位，那是另一种用法。**不改**，把前提写在这里。

### P1-5 立直棒（影响真实顺位）

`hora` / `ryukyoku` / `end_game` 在 Mortal 的 `mjai_log` 里**都不带 `scores`**，只能靠 `deltas` 累加。
旧实现只在 `reach_accepted` 扣 1000，终局却不把桌上剩下的立直棒还给头名 → 127 份里有 **7 份**
终局总分是 99000 或 98000 而不是 100000。补上「终局供托归头名」之后，127/127 全等于 100000。

顺位破平也从「相对末局庄家」改成天凤/雀魂的「绝对座次 0→1→2→3」。

另外 `logStats()` 里自摸的和了事件 `target == actor`，旧代码用 `else if` 挡住了，这次重写时曾把 `else` 丢掉，
导致自摸被算成放铳（`avg_deal` 变成负数）。已改回 `else if`，并用金标准复验。

## 七、换了新文件，能全部改完吗？

**代码层面：能。数据层面：不能，差三件事。**

1. **旧记录里存的是旧数字。**
   `games` 表存的是导入那一刻算好的 `row`（合计失分、五项指标、顺位…），不是每次打开重算。
   所以装上新版以后，历史场次仍然显示旧数字。
   → 已补：设置页「按当前口径重算全部」。它读库里存的报告原文，逐场重算、回写，
   并记下 `calc_version`；下次打开设置页会提示「已有 N 场是按 vX 口径算的」。
   （`web/js/app.js` 的 `recalcAll()`、`web/js/db.js` 的 `putGame()`）
2. **Python exe 不共享这份 JS。** 换 APK 不影响 exe，第一类问题在 exe 上仍然是坏的。
3. **两项大改还没做**：立直切牌的对齐策略（98 条里 96 条走模糊匹配）、内存架构。
   现在的 1.0.4 不含它们。

另外提醒：**改了口径，跨版本比较就没有意义了**。重算完整库之后，
以前的笔记/表格里的数字会对不上；要留档就先导出旧 CSV。
